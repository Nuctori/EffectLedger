# 可选类型行为约束：需求与保证边界

日期：2026-09-15
状态：需求已记录；不是现有能力说明，尚未开始实现。

关联文档：
- [总体实施计划](behavior-contracts-plan.md)
- [P0–P8 详细工作包](behavior-contracts-phases.md)

本文定义用户要获得什么保证及不可混淆的语义；总计划负责架构，详细工作包负责执行。三份文档不一致时，应先显式记录决策并同步，不能选择较弱解释规避验收。本次不扩大首版 P0–P6 的范围。

## 1. 目标与设计立场

用户通过一个类型级角色声明，选择一套静态可检查的行为规则，保留普通 C# 方法形状。工具检查实现及其相关依赖，定位隐藏输入、外部修改、可变别名和其他越界行为。无需先使用 Godot、资源 Claim 或 EffectLedger.Runtime。

目标不是给用户提供自我承诺的标签，而是建立一个嵌入普通 C# 项目的受限、可验证区域：只有在规则模型和列明假设内满足约束的实现，才能通过严格验收。

“极大程度减少 bug”是产品动机，不是无依据的数值承诺。需通过试点记录发现的缺陷类别、误报、未知和接入成本；不输出未经校准的 bug 概率，也不保证业务逻辑必然正确。

## 2. 声明、检查与证明的关系

### R-SEM-01 声明产生义务，不自动完成义务

接口、属性、泛型约束、Profile 和布尔值均可表达主张，但不能单独作为实现已满足该主张的证据。外部程序集或开放泛型上的 marker 同样适用。

C# 原生类型系统不理解自定义角色的语义；本模块通过额外检查落实规则。这个区别不只属于 C#：即使使用证明语言，也须区分假设、公理和已检查证明。

验收：一个实现了 ImmutableValue 角色却暴露可变对象的类型，不能因为 marker 存在而获得成功；metadata-only 类型只有声明时不能保留“源码验证”依据。

### R-SEM-02 静态检查不局限于语法禁项

实现允许并需要符号分析、数据流、抽象解释、固定点和受限证明规则。不得以“不可判定”为由将目标退化为危险 API 字符串扫描。

对任意程序的完整、准确且总能终止的通用判定不可作为承诺；这不排除对受限片段证明行为性质、协议或代数律。

验收：跨 helper 的效应传播有实际用例；后续受限证明器遇到不支持/超时返回未知，而不是声称代数律原则上无法静态验证。

### R-SEM-03 优先保守拒绝，不将未知当正确

接受某些实际上正确的代码被拒绝或要求额外证据，优先保持规则边界明确。检查能力不足、外部摘要缺失、目标不闭合或预算耗尽，必须显示未知。

这是设计目标，不是未经验证的分析器 soundness 定理。检查器缺陷仍可能导致漏报，需要测试、对抗审查和模型对照持续降低风险。

验收：unknown-only 根在 strict 模式下不通过；已支持违规不得为降低误报率被静默改成成功。原定支持形状也不能全部降成未知来冒充实现完成。

## 3. 最大约束能力与发布范围

以下是不同保证类别，不是自动包含全部下层性质的一条等级链。结果必须注明实际检查了哪些义务。

| 能力类别 | 能约束什么 | 发布范围 | 不自动保证 |
| --- | --- | --- | --- |
| 符号/结构规则 | 禁用 API、类型形状、成员写入限制 | 首版基础机制 | 跨调用的完整行为 |
| 传递性行为约束 | 隐藏输入、外部修改、深层不可变、别名逃逸 | P0–P6 首版 | 终止、业务正确、交换或线程安全 |
| 所有权/协议约束 | 借用、责任转移、释放与状态转换 | P7 后续范围 | 任意 C# 引用行为都能验证 |
| 前后置条件/不变量证明 | 返回条件、溢出/越界条件、对象不变量 | 独立后续设计，非本次首版义务 | 无需用户注解即可验证任意程序 |
| 代数性质证明 | 绑定操作在指定域与等价关系下的定律 | P8 受限片段 | 任意业务类全部操作可交换 |

### R-SCOPE-01 首版必须实质交付两个角色

ImmutableValue 与 DeterministicComputation 需具备实施计划定义的真实检查，不以声明包、仅禁 API 或空 evaluator 代替。局部变量、循环、临时集合等正常业务写法应在支持范围内可用。

### R-SCOPE-02 后续性质不能提前宣传

所有权角色、Total、自动业务证明、代数律证明均不作为首版已提供的能力。确定性不能推出不抛异常，纯性不能推出交换性，数学交换性不能推出非原子读改写的线程安全。

### R-SCOPE-03 成立域和观察范围必须明确

行为约束列明输入稳定性、依赖和环境假设。代数律必须绑定具体操作、输入域、前置条件、等价关系与观察对象；不能仅靠全类型的 Commutative=true。

同样最终状态不等于日志/返回值/失败路径相同；重试安全需要明确部分执行和外部副作用模型。

## 4. 受约束区域的边界

### R-BOUNDARY-01 检查入口、内部与出口

目标使用模式：

```text
普通 C# 边界：读取时间、配置、数据库或网络
    ↓ 转成显式稳定输入
受约束区域：不可变数据 + 可追踪的确定性计算
    ↓ 返回稳定结果或操作请求
普通 C# 边界：写入、通知、UI 等真实效应
```

这不是强制所有应用重构为固定 pipeline，而是用于解释允许行为与依赖边界。业务方法不要求额外实现 Run/Combine/Behavior。

验收：显式时间值可使用，IClock 参数不会仅因“已注入”就自动通过；构造时读隐藏环境不能被 readonly 字段洗成无条件确定性。

### R-BOUNDARY-02 防止可变别名穿透

受约束对象的可靠性不能只检查内部代码：外部保留可变输入别名、公开内部可变集合、浅复制可变元素都可能破坏保证。必须在入口、存储、构造和出口检查可达状态与逃逸。

验收：readonly List、IReadOnlyList 包装、ToArray 浅复制可变元素均不能冒充深层不可变。不得把所有 private 字段自动视为与外界隔离。

### R-BOUNDARY-03 信任闭包可见

对源码依赖自动传播摘要；对外部库、虚派发、回调和生成代码明确覆盖与未知。不能全域信任 System.*，不能自动信任 PureAttribute。

用户摘要是列明的假设；其依据、版本、条件和受影响根必须可追溯。引用源码不在当前 compilation 时，不能假装已经分析过它。

### R-BOUNDARY-04 不作为恶意代码沙箱

本工具约束授权工程的编程行为，不防御拥有修改源码、构建、策略或进程权限的攻击者。反射篡改、unsafe、原生互操作等未支持能力不能进入验证闭包而保持成功。

工程加载、MSBuild task 和生成器可能执行代码，审核工具只处理用户授权的工程，不宣传为安全运行未知工程的隔离环境。

## 5. 结果与证据需求

### R-EVIDENCE-01 多维结果，不用一个“通过”掩盖区别

报告至少独立记录：

1. 义务结论：Satisfied / Violated / Unknown。
2. 证据来源：源码规则推导、内建摘要、用户信任摘要、测试结果、受限证明结果（按阶段支持）。
3. 覆盖范围：角色/规则、根、依赖、输入域、观察模型、未覆盖节点。
4. 版本关联：引擎、规则目录、输入/配置及相关实现指纹。

同一根可同时存在已知违规、未知与信任依赖，报告不能只保留最有利的一个状态。

### R-EVIDENCE-02 测试、信任和证明不互相升级

- Tested：记录样本、种子、合法域和反例；有限随机测试通过不等于全称证明。
- Trusted：列明用户或库摘要假设；reason 是解释，不是数学证据。
- 静态约束通过：在支持模型和已列明假设下满足所检查规则，不声称检查器本身已被证明正确。
- 受限证明通过：只适用于被精确绑定和编码的义务；模型与实现对应关系必须说明。

后续求解器返回 UNSAT 也不能掩盖编码错误或前提不适用。checked/unchecked、位宽、浮点、异常等不能被替换成不相符的理想数学语义。

### R-EVIDENCE-03 可信计算基础透明

用户可见文档和报告需能说明保证依赖哪些环节：分析器实现、C# 语义模型、Roslyn/构建输入、库摘要、后续求解器/证书检查器及可选生成器。

首版不要求形式化验证整个分析器，但不得使用“绝对不会有此类 bug”“完整证明了任意 C#”等措辞。进一步验证小型检查内核可作为后续可信度提升方向，不纳入当前首版交付。

### R-EVIDENCE-04 证据随输入变化失效

实现、依赖、配置、适用域、等价关系或工具规则发生相关变化时，必须重新检查或明确标记证据失效。不复用不同 compilation 的过期 Symbol/成功结论。

## 6. 严格验收与用户体验

### R-GATE-01 严格门不能只看显示的诊断

严格审核使用内部原始检查结果及覆盖策略，不能因 pragma、NoWarn 或 editorconfig 隐藏 IDE 诊断而成功。

必须检测工具错误、生成源失败、检查预算耗尽及目标覆盖退化；零目标不能自动代表关键类型已验证。精确目标清单和最低数量检查的强度要分别说明。

### R-GATE-02 验证对象对应真实构建

按 project/configuration/TFM/引用/预处理符号/生成源/AdditionalFiles 获取一致输入；不能审核了另一个程序却对当前构建给出保证。

### R-UX-01 诊断给因果链与有效修复

显示角色、违反规则、根因符号、调用/别名链与适用边界。优先建议显式输入、冻结/复制、修正依赖，而不是让用户添加 trust 来消除红线。

### R-UX-02 不把正确性成本藏在业务接口里

用户无需逐 helper 标记或改写为固定执行框架。对真实不支持的代码可以要求边界调整或额外证据，但须明确成本；试点记录额外注解、摘要数量及方法签名变化。

## 7. 更强保证的候选路线：受限表达式/DSL

若将来需要比任意 C# 分析更强且更自动的保证，可以提供受限表达式或声明式构造，再生成 C#。按构造成立的性质通常更容易组合验证。

此路线是候选研究方向，不替代本次普通 C# 用户面，也不新增首版实现义务。

若开放任意 Func<T>/Action 回调，必须分析或显式信任回调；不能因为外围是 DSL 就忽略其中的任意 C#。生成器也属于可信计算基础，生成代码必须与已验证语义对应。
