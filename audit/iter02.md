## 逐命题审计

### P-02-1 顺序组合 `;` 定义为 ∪ 丢失执行序

| 项 | 内容 |
| ---- | ---- |
| 命题 | `(S₁ ; S₂) = S₁ ∪ S₂`（L253）是否丢失执行序信息 |
| 数学性质 | ∪ 交换 ⇒ `(S₁;S₂) = (S₂;S₁)`，`;` 作为 Signature 上的二元运算是交换的，与「顺序」一词的直观语义不符 |
| 状态 | **open** |
| 行号 | L253–L255 |

**论证**：∪ 的交换律是集合论定理，故该定义下顺序组合与反序组合所得 Signature 恒等。影响分两层：

1. **net 不受影响（此部分可消解）**：`net(S,scope)` 是对 Claim 的求和差（L315–L318），加法交换 ⇒ 执行序丢失不影响 net。子命题「`;` 对 net 充分」：discharged（前提：net 定义如 L315–L318 且 Claim 集合无重复计数，由 3.1.4a 幂等保证）。
2. **Peak 时序语义受损**：真实峰值是并发时间线上的最大同时占用量（前缀和的 max）；集合抽象只保留「出现过哪些 Claim」。对单线程顺序代码，L337 的 `max_{i∈1..ω} Σ_{c∈copy_i, mode≠release} c.size` 恰好等于全部非 release size 之和，是真实峰值的**保守上界**（先建后释场景高估、永不低估）——此方向性论断文档**未作出**，属于缺失的 soundness 声明。
3. DO-9 泄漏判定「scope 内无对应 release **配对**」（L318–L319）隐含 create/release 的一一配对结构，而 ∪ 后的 Signature 是无序集合，配对对象（哪个 create 对应哪个 release、是否同 scope 内可达）在代数层已不可恢复，只能靠 Analyzer 层控制流分析补足——文档未声明这一职责转移。

**判定**：丢序作为抽象选择本身可行，但文档缺少两条必要补充：(i) 「集合抽象给出的 Peak 是真实时序峰值的上界」的形式化声明；(ii) DO-9 配对语义从代数层移交到工具层的显式说明。二者均缺 ⇒ open。

### P-02-2 `||` 在 Compatible 不满足时的错误语义

| 项 | 内容 |
| ---- | ---- |
| 命题 | 并行组合在 Compatible 前置条件失败时是否有定义的错误语义 |
| 数学性质 | `|| : Signature × Signature ⇀ Signature` 为**偏函数**（部分函数），非全函数 |
| 状态 | **open** |
| 行号 | L260–L262 |

**论证**：L260 将 `||` 体定义为 ∪，L261 以「需满足」引入 ∀c₁∈S₁,c₂∈S₂ 的 Compatible 前置条件。这是**前置条件式定义**：条件不满足时 `||` 的值未规定——没有返回冲突标记（如 ⊥/CONFLICT 标签并集）、没有回退到顺序组合、也没有指明错误在编译期如何呈现。§14 A4（L~A4 判据）只在 Analyzer 层提「报警」，代数层自身不闭合。后果：

- 代数不是自包含的演算：含 `||` 的合法项可能无值，后续 net/Peak 对此类项无定义，违反「审计代数应 total 化以便机械求值」的自设目标（对比：⊔ 在 L285 显式声明为全函数签名 `Signature × Signature → Signature`，二者不对称）。
- 冲突信息被丢弃：即使想报「哪一对 Claim 冲突」，∪ 的结果中也无法定位（幂等吞并）。

**最小补充**：将 `||` total 化，例如 `(S₁||S₂) := S₁∪S₂` 附带冲突对集合 `ConflictPairs(S₁,S₂) := {(c₁,c₂) | …¬Compatible…}` 作为派生量，或定义带标签域 `Signature ⊔ {⊥CONFLICT}`。

### P-02-3 Compatible 对称性（文档标注 P1）

| 项 | 内容 |
| ---- | ---- |
| 命题 | `Compatible(m₁,m₂) = Compatible(m₂,m₁)`（L276） |
| 数学性质 | 二元关系对称性 |
| 状态 | **discharged**（文档原为 asserted；此处给条件证明） |
| 行号 | L268–L276 |

**条件证明**：前提 A1：mode 论域恰为 `{use,create,release,move}`（L90），不含其他值；前提 A2：命题逻辑析取可交换。
定义（L268–L272）每个析取支成对出现：`(m₁=create∧m₂=release) ∨ (m₁=release∧m₂=create)` 等，变量互换即得另一支；首支 `(m₁=use)∨(m₂=use)` 交换后不变。故逐支验证 16 对：对任意 (m₁,m₂)，φ(m₁,m₂) 中某支为真当且仅当 φ(m₂,m₁) 中对称支为真。∎
闭合式（L274）一致性：`use` 支对称；`∉CONFLICT` 支对称，因为 CONFLICT（L273）仅含对角元 `(m,m)`，对角集的补关系必对称。∎

### P-02-4 `||` 的交换性

| 项 | 内容 |
| ---- | ---- |
| 命题 | `(S₁||S₂) = (S₂||S₁)` |
| 数学性质 | 算子交换性 |
| 状态 | **discharged**（文档未断言，审计补证） |
| 行号 | L260–L261 |

**条件证明**：前提 B1 = P-02-3（Compatible 对称，已证）；前提 B2：resource 相等 ≡ 是对称关系（3.1.4a L174–L190 的归一化相等为逐字段相等/映射双射，对称）。则：
(i) 函数体：`S₁∪S₂ = S₂∪S₁`（集合交换律）；
(ii) 前置条件：`∀c₁∈S₁∀c₂∈S₂ (c₁.res=c₂.res ⇒ Comp(c₁.mode,c₂.mode))` 与反向量词式经 B1/B2 逐对等价。∎

### P-02-5 条件组合 `⊔` 的配对键自吞（size 参与相等判定）

| 项 | 内容 |
| ---- | ---- |
| 命题 | L286「⊔ 按 Claim 相等（3.1.4a）配对……对二者 size 区间取 merge_I」能否实现其宣称的区间合并 |
| 数学性质 | 配对谓词含 size ⇒ 可配对者必同区间 ⇒ merge_I 限制在恒等输入上：`∀(c₁,c₂) 可配对: c₁.size=c₂.size=[a,b] ∧ merge_I([a,b],[a,b])=[a,b]`（merge_I 自反性，L235） |
| 状态 | **open（文档内部矛盾，高优先）** |
| 行号 | L284–L291、L175、L232–L236 |

**论证（自吞反例链）**：
1. 3.1.4a 第 (3) 条（L175）：Claim 相等的判定**包含** size 的区间相等 `[s,s]=[s,s]`。
2. L286 以 Claim 全等作配对键 ⇒ 仅 size 完全相同的两条 Claim 进入 merge_I 分支。
3. 于是 merge_I 的输入恒为 `([a,b],[a,b])`，输出 `[a,b]` —— **merge_I 分支是死代码**；L287 宣称的 `[min(lo₁,lo₂), max(hi₁,hi₂)]` 在该配对规则下永不可达（min/max 恒取等值）。
4. `⊔` 因此逐点退化为普通集合并，L289「join-semilattice 的 join」虽平凡成立但无区间语义内容。

**反例（净额错算）**：设 `S₁={occupy(mem,create,[10,10])}`，`S₂={occupy(mem,create,[20,20])}`，二者 kind/resource/mode/scope 全同、仅 size 异 ⇒ 按 L175 不相等 ⇒ 不配对 ⇒ 输出集合含**两条**独立 Claim。代入 net（L315）：`net = 10 + 20 = 30`；而条件分支的真实互斥语义应为区间 `[10,20]`。净额被高估 50%，且该误差随分支数线性放大。这直接削弱 AUDIT003 类预算比较（L~§12.2）的正确性。

**附带矛盾**：L288「仅一处出现的 Claim：size = 其单值区间 [s,s]」强制单值化——输入 Claim 本可携带开区间 `[lo,hi]`（如动态 Instantiate 的 `[1,⊤]`，L216–L217），此处会被错误改写为不存在的「单值」。措辞应改为「size 保持其原有区间」。

**最小补充（消解路径）**：配对键改为四元组 `(kind, resource, mode, scope)`（剥离 size），命中者对 size 施加 merge_I，未命中者保留原区间。修改后 `⊔` 成为真正的区间 join-semilattice，且 L289 性质变为实质成立。

### P-02-6 循环组合 `S × ω` 中 ω 是否实际进入度量

| 项 | 内容 |
| ---- | ---- |
| 命题 | L296 `(S × ω) := Σ_{i=1..ω} copy_i(S)` 定义的 ω 能否传导到 net/Peak |
| 数学性质 | Signature = ImmutableHashSet<Claim>（幂等并）；copy_i 同 scope 标注 ⇒ copy_i 两两相等 ⇒ `⋃_{i=1..ω} copy_i(S) = S`，与 ω 无关 |
| 状态 | **open（高优先，DO-8 定义层失效）** |
| 行号 | L294–L301、L327、L337 |

**论证**：对 L296 存在两种解读，均不通：

- **解读一（Σ = 集合多重并）**：copy_i 的 scope 统一标注为所在 `Loop(id)`（L296 注释），各副本携带完全相同的 Claim 集（3.1.4a 相等）⇒ 并集幂等吞并 ⇒ `(S×ω) = S` 对一切有限 ω 成立。下游 Peak（L327/L337）形如 `max_{i∈1..ω} Σ_{c∈copy_i(S)} …`，诸 copy_i 相等时 max 取到同一个值——即单次迭代的占用和，**ω 从未以乘法进入任何度量**。推论：`for i in range(1000): Instantiate(...)` 与执行一次的 Signature 完全相同，DO-8「循环内资源分配静态报警」在代数层无支撑（ω=⊤ 的兜底，L297/L301，只覆盖未知次数情形，对已知 ω≥2 的有限循环同样漏报）。
- **解读二（Σ = size 层乘法 ω·size）**：则 `S×ω` 的产物不是 Claim 集合（Claim 无「ω 份」的编码字段），类型不闭合、无法落回 Signature；且即便强行乘入 size，「每轮释放后重建」与「持续累积」两类循环将得到相同结果——二者的区分恰恰需要 P-02-1 已指出被 ∪ 抹除的执行序/生命周期信息。

**结论**：`S × ω` 在当前定义体系内要么退化为恒等算子（ω 失效），要么类型不良（Σ 无定义）。文档历史残留注释（L299–L300）承认旧 cardinality 形式废弃，但新 size-求和形式并未接住 ω。**这是 rA 系列修订声称收口 iter18/iter35（L294）后的残余核心缺口。**

**最小补充**：显式定义副本可分辨机制，二选一：(a) copy_i 的 scope 标注为 `Loop(id, i)`（携带迭代索引），并重定义 Peak/net 的聚合方式（如 `Peak = Σ over iterations of per-iter occupancy`，配合 release 配对决定累加或重置）；(b) 直接定义 `Scale(S,ω) := 将 S 中每条 occupy-create/move Claim 的 size 替换为 ω·size`（⊤ 律按 3.1.5a），并在文档声明其为保守上界语义。

### P-02-7（附带）闭合式与 P4 的 Unknown 语义矛盾

| 项 | 内容 |
| ---- | ---- |
| 命题 | L274 闭合式 `Comp(m₁,m₂) ⇔ use∨use∨∉CONFLICT` 与 L279 P4「mode=Unknown 按 use 处理（fail-closed 保守兼容）」是否相容 |
| 状态 | **open（低优先，措辞级矛盾）** |
| 行号 | L90、L274、L279、L701–L702 |

**论证**：mode 论域在 L90 封闭为四值，不含 Unknown；但 §8.1 默认规则（L701）确实产出 `mode=Unknown` 的 Claim。于是：
- 若 Unknown 属域外：P4 是域外公理，不在 16 对全函数范围内，P2「16 对全覆盖」的完备性主张对实际出现的五类 mode 失效；
- 若 Unknown 视作第五值代入闭合式：`(Unknown,create)∉CONFLICT ⇒ Compatible=true`，即**放行**——这与 P4 及 L701「fail-closed」「需人工确认」的保守拦截措辞直接相反。闭合式会把一切未列入 CONFLICT 的 mode 对（包括任何未来扩展）自动判兼容，fail-closed 名存实亡。
